# BOONO V4.3 — Setup causal, contexte MCB 1H et limites structurelles — 04/10/2026

## Problème démontré

V4.2 n'a pas résolu le churning :
- 17 premiers trades V4.2 : 2 gagnants, 15 perdants, environ -10.20 USD ;
- sans le bon LONG #39 : 1 gagnant sur 16, environ -13.90 USD ;
- sur la fenêtre #39→#50, BOONO a été exposé environ 95.8% du temps ;
- 15 changements de direction sur 16 transitions V4.2 observées.

Conclusion :
[DÉMONTRÉ] BOONO transformait encore trop facilement chaque oscillation locale en opportunité tradable.

## Clarification Benjamin

1. Après création d'un setup, toute preuve microstructurelle antérieure est oubliée pour l'admission.
2. **MCB n'est jamais oublié** : la structure MCB peut parfaitement être antérieure au setup ou à la dernière sortie.
3. Une preuve fraîche `net3m` n'est pas suffisante à elle seule.
4. Le contexte MCB supérieur est central :
   - 1H sert de pont décisionnel ;
   - 4H/D sont affichés en shadow seulement afin de ne pas devenir trop invalidants à notre échelle.
5. La synchronisation 3m↔15m est un facteur central ; la cohérence avec 1H renforce fortement l'opportunité.
6. MA200, trendlines et niveaux ne choisissent pas la direction mais doivent pouvoir dire qu'un mouvement arrive sur une limite et que le combat n'est pas encore résolu.

## Architecture V4.3

Version :
`v4.3-setup-context-20261004`

### 1. MCB BACKGROUND — central

Nouveau module :
`modules/v4/layers/mcb-background.js`

- 1H = contexte primaire/actionnable.
- 4H + Daily = qualification shadow, `decisionImpact=false`.
- La direction d'un TF n'est pas simplement `LBW > 0`.
- Le moteur lit :
  - lobe courant ;
  - récupération depuis l'extrême ;
  - pente LBW ;
  - retournement interne éventuel.

Relation de la candidate locale au 1H :
- `WITH_BACKGROUND`
- `AGAINST_BACKGROUND`
- `UNKNOWN`

Une candidate contre le 1H n'est pas interdite, mais sa maturation devient plus exigeante.

### 2. Synchronisation 3m / 15m / 1H

Le 15m fournit la candidate locale MCB.
Le 3m décrit la construction interne du mouvement.

Pour armer un setup :
- le 3m doit être cohérent avec la candidate 15m ;
- si la candidate est `AGAINST_BACKGROUND` 1H :
  - le 15m doit être `MATURE_REVERSING` ;
  - la candidate doit provenir de `REVERSAL_FORMING` ;
  - le 3m doit être explicitement `TURN_ALIGNED`, et non seulement se trouver dans un lobe du même sens.

Ainsi un trade contre le fond paie un coût de preuve plus élevé.

Le 4H/D ne bloquent rien. Leur cohérence est exposée comme :
- `STRONG_WITH_BACKGROUND_SHADOW`
- `STRONG_AGAINST_BACKGROUND_SHADOW`
- `MIXED_SHADOW`

## 3. Limites structurelles = attente du résultat du combat

Nouveau module :
`modules/v4/layers/structural-room.js`

Sources :
- MA200 15m ;
- niveaux S/R ;
- trendlines actives déjà disponibles dans BOONO.

États :
- `OPEN_PATH`
- `APPROACHING_BOUNDARY`
- `BOUNDARY_CONTEST`

Principe :
- une limite ne dit jamais LONG/SHORT ;
- une limite située **devant** la candidate et actuellement combattue suspend la création du setup ;
- une MA située derrière le mouvement ne bloque pas ;
- lorsque le prix a réellement dépassé la zone de contestation, le chemin redevient exploitable.

C'est une correction importante de la lecture précédente :
`interaction MA200` n'est pas en soi négative ; c'est le fait d'extrapoler une poussée **dans une limite non résolue** qui est incorrect.

## 4. Lifecycle précis

V4.3 n'utilise pas `CANDIDATE/FRESH/FORMING` comme états vagues.

### OBSERVE

Il existe une lecture MCB candidate mais les conditions structurelles ne sont pas encore réunies.

Raisons explicites possibles :
- `WAIT_3M_15M_SYNC`
- `AGAINST_BACKGROUND_NEEDS_REVERSING_15M_AND_3M_TURN`
- `BOUNDARY_CONTEST`
- `DORMANT_MARKET`
- `THESIS_CONSUMED_WAIT_MCB_CHANGE`

Aucune admission.

### SETUP

Un setup est créé quand :
- direction locale MCB identifiable ;
- 3m/15m cohérents ;
- contrainte 1H respectée ;
- aucune limite structurelle non résolue devant la candidate ;
- marché pas explicitement dormant ;
- la même thèse/setup n'a pas déjà été consommée.

À ce moment :
`setupTs = maintenant`.

### PREUVE POST-SETUP

À `setupTs`, les preuves d'admission repartent de zéro :
- `netSinceSetup`
- `grossSinceSetup`
- `efficiencySinceSetup`
- persistance ticker post-setup.

Les données antérieures restent disponibles comme **baseline de calibration** p75/p95, mais elles ne comptent plus comme preuve causale d'une nouvelle entrée.

### CONFIRMED / ENTER

Seulement après :
- traduction PM construite depuis `setupTs` ;
- ticker confirmé uniquement avec observations postérieures au setup.

### CONSUMED

Une fois utilisé par une position, le setup est consommé.

Après sortie :
- MCB historique et contexte restent intacts ;
- PM/ticker de l'ancienne admission sont invalidés ;
- le même `setupKey` MCB ne peut pas être repris ;
- un changement réel de candidate/mode/lobe/synchronisation produit un nouveau setup possible.

Cela évite de recycler exactement la même thèse périmée tout en permettant au MCB antérieur de rester la mémoire structurelle du marché.

## 5. PM/ticker frais

`price-translation.js` et `ticker-confirmation.js` acceptent maintenant `sinceTs`.

En admission V4.3 :
- les baselines historiques servent seulement à savoir ce qui est inhabituel ;
- le déplacement et la persistance utilisés comme preuve doivent être postérieurs au setup.

Le moteur expose :
- `entryTranslation`
- `entryTicker`

séparément des mesures rolling utilisées pour comprendre/gérer une position déjà ouverte.

## 6. Marché dormant vs hachoir

Nouveau module :
`modules/v4/layers/market-quality.js`

Mesures natives :
- net 30/60m ;
- gross 30/60m ;
- efficiency ;
- range ;
- fréquence des changements de camp.

Pour l'instant :
- `DORMANT` peut suspendre un setup ;
- `CHOP_SHADOW` est **informatif seulement**.

Le hachoir n'est pas encore un veto parce que le bon trade #39 est apparu dans une période globalement peu efficace ; le bloquer brutalement risquerait de supprimer une vraie sortie de compression.

Le seul blocage d'activité utilise une référence économique :
- range 30m < 20% de 220 USD (=44 USD)
- ET gross 30m < 50% de 220 USD (=110 USD)
→ `DORMANT`.

Cette règle est volontairement étroite et devra être évaluée.

## 7. Contre-factuel background sur la série #39–#50

Reconstruction historique 1H :
- #39 LONG gagnant → `WITH_BACKGROUND`.
- #40 SHORT perdant → `AGAINST_BACKGROUND`.
- #42 SHORT → `AGAINST_BACKGROUND`.
- #45 LONG → `AGAINST_BACKGROUND`.
- #47 LONG → `AGAINST_BACKGROUND`.
- #48 SHORT → `AGAINST_BACKGROUND`.
- #50 SHORT → `AGAINST_BACKGROUND`.

Avec la règle de maturation contre-background :
- #40 : bloqué (15m seulement MATURE, pas MATURE_REVERSING).
- #42 : bloqué.
- #45 : bloqué (3m seulement lobe aligné, pas TURN_ALIGNED).
- #48 : bloqué.
- #50 : setup contre-background suffisamment mature localement, mais son activité 30m très faible tombe dans DORMANT.
- #47 peut rester admissible : il faudra l'évaluer avec la preuve post-setup.

Important :
ceci est un contre-factuel partiel d'admission, pas un backtest complet des trajectoires.

## 8. Point important sur #39

Une première idée imposant « nouvelle structure MCB postérieure à la dernière sortie » aurait bloqué le bon #39.

Elle a donc été rejetée.

C'est conforme à la clarification de Benjamin :
**MCB persiste à travers une sortie. Ce sont les preuves microstructurelles d'admission qui repartent à zéro.**

Le bon #39 pouvait donc conserver son contexte MCB antérieur, créer un nouveau setup LONG lorsque la lecture locale changeait, puis demander une nouvelle preuve PM/ticker.

## 10. Position héritée lors de la migration

Au moment de l'activation V4.3, une position LONG ouverte sous V4.2 était encore active.

Elle conserve :
- son `version` d'entrée V4.2 ;

Le moteur V4.3 gère seulement sa suite/sortie.
Le journal de sortie stocke désormais aussi `exitEngineVersion`, afin de ne plus attribuer rétroactivement une admission ancienne à une nouvelle version.
